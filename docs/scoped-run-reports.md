# Scoped run reports

`report-run` summarizes an existing run without making a model call, executing Python, or
rerunning its numerical comparisons. It creates an internal draft for an Abt staff member
to review. The report is not automatically approved for CMS release.

This version supports the existing bounded Mortality bundle, an individual synthetic
local-model attempt, and Program 0 candidate runs. It does not support suite indexes, numeric
reassessment indexes, or a complete CMS pipeline. Issue #52 stays open until reporting can
consume the integrated pipeline's results and Abt confirms the final handoff fields.

## Program 0 run summaries

After running a Program 0 candidate, summarize its saved directory:

```text
python -m sasguard.cli report-run reports/runs/program0-candidate-<UUID>
```

The short handoff names all three declared artifacts and their recorded checks. It preserves
the original input mode, separates collection from validation, and states the full-pipeline
and CMS-rating limits. Counts in the technical report are artifact rows, not final hospital
eligibility or processing totals. Known file-level validation failures are described by status
and artifact name; raw error messages and provider-key lists are not copied into reports.

Program 0 execution records do not establish who authored the code or whether a model generated
it. Both claims remain `not_recorded`, including when a person knows the run was a human control.
Likewise, a successful process or a PR review is not a recorded human review of this run.

New runs using the real validator wrapper record policy snapshots, exact statistic rows,
validator/configuration/loader hashes, trusted-reference hashes, and the candidate and collected
output hashes. The wrapper checks those files before and after comparison. The reporting reader
checks the saved snapshots against current files and the protected baseline; it never repeats
the numerical comparison. `N`, `MIN`, and `MAX` are exact; moment tolerances stay in the recorded
policy. The technical report shows both rules.

A passing Program 0 scope is `VERIFIED` only when all three passing SAS comparisons and their
recorded execution, source, staged input, output, policy, and reference evidence agree. An older
run without a validation snapshot can still be summarized, but its recorded pass is
`NOT VERIFIED`, not evidence that the current policy ran. Changed evidence also removes the
verified claim. This remains a summary of trusted host-produced records, not a signed attestation.

## Generate a report

Run from the repository root with the host Python environment active. The same command works
in Windows PowerShell and macOS zsh:

```text
python -m sasguard.cli report-run reports/runs/mortality-<UUID>
```

For an individual synthetic attempt generated by the separate model-testing work:

```text
python -m sasguard.cli report-run reports/runs/local-model-smoke-<UUID>
```

Without environment activation, replace `python` with `.\.venv\Scripts\python.exe` on Windows
or `./.venv/bin/python` on macOS. Generation itself does not require Docker or Ollama to run.
Use the existing [Mortality prototype](mortality-prototype.md) to produce a Mortality bundle
if needed. That earlier execution does require Docker.

The command prints the new directory under ignored `reports/runs/handoff-<UUID>/`. It contains:

* `handoff.md`, a short scope and status summary, with an internal-draft warning.
* `technical.md`, aggregate validation diagnostics, policies, image identity, and evidence hashes.
* `report.json`, the same privacy-limited facts and explicit status fields for software use.

To select a destination, append `--output-directory reports/runs/my-review-draft`. It must be
a new directory, separate from the source run. Existing files and directories are never
overwritten. Both input and output must be direct child directories of `reports/runs/`.
The resolved run store must stay inside the project. Symlinks or Windows junctions that
redirect `reports/` or `reports/runs/` outside the project, or back to its root, are rejected.
Nested candidate output directories are not accepted as host-produced run evidence.
The original run is read-only to the renderer. Use a completed or stopped run, not one whose
controller is still writing metadata. This is a saved-record summary, not a live monitor.

Exit code 0 means the draft was written. It does not mean the run passed validation.
Exit code 2 means the input was unsupported, malformed, missing, or could not be written safely.
Read `scope_status` and `pipeline_status` in the output rather than treating report generation
as a correctness test.

## Claims and trust boundary

The report separates code origin, model generation, execution, deterministic comparison, and
human review. A PR approval is not a recorded review of a particular run. Human review is
therefore `not_recorded` in this version. Manual changes are also not inferred. Mortality
repair counts come from its manifest; absent synthetic repair metadata stays unknown.

For Mortality, `VERIFIED` applies only to its declared scope when successful execution, passing
SAS-reference comparison, frozen policy, matching sidecars, matching source/input/output
hashes, and the current protected-reference checks agree. It does not imply that Program 0
was reproduced. Mortality uses the supplied standardized intermediate as an input boundary.
Its handoff includes the matched provider-row and column counts when those counts are
available and agree. These describe the saved Mortality comparison, not pipeline-wide
hospital processing totals. Failed, synthetic, and unconfirmed runs do not get that match claim.

A recorded generation, execution, or comparison failure produces `FAILED` when the evidence
is consistent. Missing validation, conflicting records, or unconfirmed hashes produce
`NOT VERIFIED`. A synthetic pass is always `NOT VERIFIED` against SAS because its expectations
were handwritten. A synthetic mismatch may still be `FAILED` against those expectations.

The renderer does not silently replace historical comparison policies. For example, a saved
pass under an older inferred numeric policy remains a recorded pass, not a claim that a
stricter policy ran. The technical section identifies that policy as `legacy_inferred` when
the source record has no named contract. Separate reassessment results require a future
adapter, not a relabeling of the original attempt.

Full-pipeline status is always `NOT VERIFIED` in this first version. Hospital processing and
eligibility totals and final ratings stay null. Artifact row counts are shown only as artifact
row counts. The original command is not reconstructed from logs or reported as known when
the source record never stored it. First observed failures identify artifact checkpoints,
not the exact SAS statement or root cause.

These are summaries of trusted host-produced records, not signed attestations. Hash matching
detects changes relative to those records and the locally declared protected baseline. It
does not prove that an attacker has not rewritten both records and their hashes. Native
Mortality policy/configuration must match the controller's frozen July 2025 configuration.

## Privacy and release review

Neither readable section nor `report.json` contains raw stdout, stderr, prompts, model
responses, generated source, input rows, expected rows, or row-level missing/extra provider
identifiers. Only counts and schema-level diagnostics are projected from comparison results.
Unrecognized fields in a synthetic record are not copied into the report. Markdown escapes
schema metadata rather than treating it as HTML.

This is not a general secret scanner. Abt must still review metadata, schema names, aggregate
diagnostics, and both documents before choosing what to send outside the team. Reports remain
local and ignored by Git by default. Do not automatically publish `technical.md` with the
short handoff summary. PDF generation, a web interface, and final client-release approval are
outside this first version.
